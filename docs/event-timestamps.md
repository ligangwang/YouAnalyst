# Event Timestamp Requirements

## Goal

Standardize the three timestamps used by YouAnalyst events:

1. `published_at`
2. `collected_at`
3. `processed_at`

Each timestamp has a different semantic meaning and must not be used
interchangeably.

---

## 1. published_at

### Definition

The time when the information became publicly available according to the
original source.

Examples:

- IR/news release → publisher's publication datetime
- SEC filing → SEC acceptance datetime
- News article → article publication datetime
- X post → post creation datetime
- GitHub release → release publication datetime

### Usage

`published_at` is the primary business/event timestamp.

Use it for:

- Investor-facing event datetime
- Event sorting
- Event feed ordering
- Graph Universe event positioning
- Event timeline
- Historical replay
- "Latest events" queries
- Event clustering based on occurrence/publication time
- Market-price reaction calculations
- Relative time such as "8 min ago"

### UI visibility

Visible to all users.

Example:

    AMD announces MI450 update
    Oct 2 · 4:05 PM ET

For U.S. equities, display in America/New_York (ET) by default.

### Important

Never substitute `collected_at` or `processed_at` for `published_at`
when determining when an event happened.

---

## 2. collected_at

### Definition

The first time YouAnalyst successfully detects or ingests the source item.

This timestamp is generated by YouAnalyst, not by the external publisher.

Example:

    published_at = 4:05:13 PM
    collected_at = 4:05:41 PM

YouAnalyst detected the event 28 seconds after publication.

### Usage

Use `collected_at` for operational monitoring only.

Examples:

- Collector latency
- Collector SLA
- Detecting slow/stale collectors
- Troubleshooting ingestion
- Comparing collector performance
- Admin monitoring

Collection latency:

    collected_at - published_at

### UI visibility

ADMIN ONLY.

Do NOT expose this timestamp in normal investor UI.

---

## 3. processed_at

### Definition

The time when YouAnalyst finishes processing the collected item and the
normalized event becomes available to downstream YouAnalyst applications.

Example:

    published_at = 4:05:13 PM
    collected_at = 4:05:41 PM
    processed_at = 4:05:44 PM

### Usage

Use `processed_at` for pipeline monitoring.

Examples:

- Processing latency
- Pipeline SLA
- Detecting processing bottlenecks
- Debugging
- Measuring end-to-end event availability
- Admin monitoring

Processing latency:

    processed_at - collected_at

End-to-end latency:

    processed_at - published_at

### UI visibility

ADMIN ONLY.

Do NOT expose this timestamp in normal investor UI.

---

# 4. Timestamp Relationship

Normal successful event flow:

    published_at
         ↓
    collected_at
         ↓
    processed_at

Example:

    Published     16:05:13
         ↓ 28 sec
    Collected     16:05:41
         ↓  3 sec
    Processed     16:05:44

Collection latency = 28 sec
Processing latency = 3 sec
End-to-end latency = 31 sec

---

# 5. Storage

Store all three timestamps internally in UTC.

Example:

{
  "published_at": "2026-10-02T20:05:13Z",
  "collected_at": "2026-10-02T20:05:41Z",
  "processed_at": "2026-10-02T20:05:44Z"
}

Convert timezone only for presentation.

Do not store ET-converted values as canonical timestamps.

---

# 6. Investor UI Rules

Investor-facing UI uses:

    published_at

ONLY.

Examples:

Event feed:

    AMD announces MI450 update
    4:05 PM ET · AMD Investor Relations

Graph Universe:

    Event appears at 4:05 PM ET

Timeline:

    4:05 PM ── AMD event

Historical replay:

    Event activates at published_at.

The time at which YouAnalyst happened to collect/process the event must not
move its position in historical timelines.

---

# 7. Admin UI Rules

Admin UI may show all three:

    Published       4:05:13 PM ET
    Collected       4:05:41 PM ET      +28 sec
    Processed       4:05:44 PM ET       +3 sec
    -------------------------------------------
    End-to-end                              31 sec

This information is for monitoring the health and performance of the
YouAnalyst event pipeline.

Admin authorization must be enforced server-side, not merely by hiding UI
fields.

---

# 8. Missing published_at

Do NOT silently use `collected_at` as `published_at`.

If the source does not provide a reliable publication datetime:

    published_at = null

Optionally maintain timestamp precision/source metadata separately.

The investor UI can fall back to a less precise source date if one exists,
but must not represent YouAnalyst collection time as the publisher's
publication time.

Example:

Source provides:

    October 2, 2026

Display:

    Oct 2

Do NOT manufacture:

    Oct 2 · 12:00 AM

and do NOT display `collected_at` as though it were the publication time.

---

# 9. Sorting Rules

Investor event ordering:

    published_at DESC

Operational/admin ingestion ordering:

    collected_at DESC

Operational/admin processing ordering:

    processed_at DESC

Do not accidentally order investor-facing feeds by collection or processing
time.

---

# 10. Naming

Use these exact semantics consistently throughout backend, APIs, Firestore,
frontend and analytics:

published_at
    External/source event time.

collected_at
    YouAnalyst ingestion time.

processed_at
    YouAnalyst processing completion time.

Do not use ambiguous names such as:

    event_time
    timestamp
    date
    ingest_time

unless they are clearly mapped to one of the three canonical timestamps.
