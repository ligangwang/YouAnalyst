# Initial intelligence payload

The homepage embeds a compact graph-only universe when it is ready within the HTML budget. Graph rendering does not await feed discovery, collector freshness, news projection or the complete source-document index. A slow graph read retains the existing browser bootstrap. Existing full-snapshot callers still reuse their server feed without an immediate duplicate request.

After resolving the published theme, a small preload component renders outside the graph's waiting boundary. It emits a low-priority `as=fetch` hint for the exact initial graph-free compact feed URL. The browser starts that request before hydration; the hook's existing `cache: no-store` fetch consumes the document preload rather than starting another request. No-store still prevents HTTP caching across navigations. Scoped company/search/region/event/relationship links skip this generic hint and retain their dedicated requests. Desktop/mobile tests use a real HTTP server, a no-store response, delayed hydration and the actual preload component to verify one request. Browsers that ignore the hint retain the existing fetch behavior. Events and totals remain explicitly pending until their feed arrives.

An earlier server-streamed feed experiment was blocked before promotion because it slowed graph readiness. The final page does not start feed discovery on its server render or serialize a feed Promise; the browser schedules the independent feed instead.

The browser opts into `graph=omit&payload=compact` on its initial feed request. This response carries graphVersion and the first 20 detailed events, while retaining the complete sourceDocuments facts, coverage and source totals. Legacy API callers retain the complete response unless they explicitly opt in. No persisted schema changes are involved.

Graph-bearing server props and browser bootstrap requests use the lossless `columns-v1` graph transport. Each node, relationship and source table sends field names and distinct values once, followed by rows of dictionary indices (`-1` means an absent property). This removes repeated theme metadata and field names without dropping descriptions, evidence, translations or search fields. The client restores the ordinary graph before existing workspace logic runs, and the original graphVersion remains authoritative. API callers opt in with `graph=compact`; the default response stays compatible with existing clients. Feed updates still omit the graph entirely.

Server props carry the column graph as one JSON text block (`columns-json-v1`), avoiding React Flight's traversal of individual dictionary cells. The JSON API continues to send `columns-v1`. Both decode to the same complete graph. A local Flight serialization check took about 48 ms for column objects versus 6 ms for the text block.

The graph view emits server-side resource hints through `next/dynamic` outside the data Suspense boundary. These hints start the exact 3D scripts from the first HTML without waiting for hydration or a snapshot. A preload-only component renders no canvas and primes the same module used by the workspace. Browser module initialization and browser-only loading reuse that request. Direct table/tree/hierarchy visits retain lazy loading. The isolated release check verifies graph script hints while its fixture has no intelligence snapshot, and verifies those hints are absent for direct table visits. Failed preloads are observed and clear the pending loader so a later render can retry.

Production compares five interleaved samples on the zero-traffic candidate and serving site, each in a fresh browser process to avoid carrying GPU state between samples. Each target gets one excluded warmup. Complete-page readiness is the later of the first rendered graph frame and settled feed, calculated per load before taking the median. More than 10% regression in that median or in feed readiness blocks promotion. The graph median may be at most one second later, bounding the first-frame tradeoff while prioritizing a usable complete page. Empty feeds count as ready, and failed readiness checks log both signals before blocking traffic changes. Functional checks and monitored promotion remain required. Cold, fresh-browser and cached-refresh timings are reported separately.

Browser navigation uses the same bounded tagged-route 404 readiness probes as functional validation. Every failed navigation is logged; persistent 404s and all other HTTP errors block the release. Timing starts on the final successful document navigation, not an infrastructure error page. App readiness failures retain page title, initial visible text and failed-request diagnostics.

November 7, 2026 graph sample: 3,912,203 decoded bytes becomes 2,550,018 bytes; gzip at the same settings drops from 687,836 to 640,805 bytes. Full graph round-trip equality is verified, including source facts. Three fresh desktop baseline graph mounts were 4.308, 8.322 and 4.002 seconds (median 4.308 seconds). Production candidate and public after-release measurements are recorded separately under the release worktree's output directory.

Graph and feed bootstrap requests run in parallel. The browser only combines a graph-free feed with a graph of the same version, fetching a replacement when necessary. Older scopes/themes are fenced by the existing cancellation checks. Feed polling and scope updates omit the graph too.

Period/source/sector/watchlist filters, company/search scopes, deep links and Show more request the complete event set on demand. Totals continue using the complete source-document facts. During expansion the event pane shows its pending/error state; it cannot imply the first page is the whole filtered result. Existing previous-day loading remains available.

Baseline production measurements on November 6, 2026: graph payload 3,911,927 decoded bytes; feed 5,803,745 decoded bytes including that graph, 1,669 events and 1,651 source documents. Combined API payload was approximately 9.7 MB decoded, approximately 1.6 MB transferred with compression. Three fresh desktop graph mounts took 10.4–17.6 seconds; a normal cached refresh took 12.4 seconds. These local Playwright measurements are not a representative user benchmark. Candidate and post-release timings are recorded separately during rollout.
